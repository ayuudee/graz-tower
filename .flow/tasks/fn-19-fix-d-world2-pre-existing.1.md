### Step 2 — Reshape `assertExpectedLjmbIfrSids` helper body (R1, R2, R3)

Open `migration/src/jvmTest/kotlin/xyz/easiersaid/twr/migration/world/LjmbWorldCandidateValidationTest.kt:252-270`. **Keep the existing helper signature** (`private fun assertExpectedLjmbIfrSids(document: WorldCandidateDocument)`); only the body changes. The single `@Test fun writesLjmbCurrentCoreValidationReport()` at line 114-115 is unchanged — it still calls this helper.

Recommended shape (per plan-review round 1 — decomposition is two inner `private fun`s within the test class, not two new @Test methods):

- **`assertSidsAreStructurallyValid(document)`** — loops over `document.world.aerodrome.sids` entries, validates each: (a) the map key equals the `sid.id` field on the value, (b) a matching `_PATH` entry exists in `document.world.geometry.paths`. **No hard-coded set**. Map-key duplication is not checkable post-decode (kotlinx.serialization decodes into `Map<String, Sid>`); skip that check. Catches future SIDs that break parsing or path-projection. Unexpected SIDs are NOT a failure here.
- **`assertSidsCoverPromisedSet(document)`** — `private val expectedCovered = setOf("LJMB_SID_GOLV2G_14", "LJMB_SID_PETO2B_14", "LJMB_SID_PETO5D_32", "LJMB_SID_VALU1S_14", "LJMB_SID_VALU4L_32")` (full map-key ids per `document.world.aerodrome.sids.keys` — NOT short names; verified in the current `world-candidate.json`). Asserts `missing = expectedCovered - actual` is empty. **Does NOT assert `unexpected = actual - expectedCovered` is empty** — new SIDs appearing in the candidate (e.g. from a CIFP cycle upgrade or M1 lifting fixless-leg blockers) are NOT a coverage regression; they're a structural validation surface only.

`assertExpectedLjmbIfrSids` becomes:
```kotlin
// SHAPE ONLY — not implementation:
private fun assertExpectedLjmbIfrSids(document: WorldCandidateDocument) {
    assertSidsAreStructurallyValid(document)
    assertSidsCoverPromisedSet(document)
}
```

The two-helper decomposition is the recommended shape; if impl-review feedback prefers keeping the single helper body inline with two clearly-named failure modes, that's acceptable as long as **the two semantically distinct failure modes produce separately-named failure messages** (a structural failure must read differently from a coverage failure).
