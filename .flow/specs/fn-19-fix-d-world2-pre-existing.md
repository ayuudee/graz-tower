# fn-19 — Fix D-WORLD.2 pre-existing :migration:jvmTest failure (LjmbWorldCandidateValidationTest 9-vs-5 SIDs)

## Overview

`migration/src/jvmTest/kotlin/xyz/easiersaid/twr/migration/world/LjmbWorldCandidateValidationTest.assertExpectedLjmbIfrSids` (a `private fun` helper called by the `writesLjmbCurrentCoreValidationReport` `@Test` at line 114-115) asserts a 9-SID hard-coded expectation (`DIML1S, GOLV1S, GOLV2G, MURE1S, PETO1S, PETO2B, PETO5D, VALU1S, VALU4L`) but the LJMB world-candidate at `cad/airports/rendered/ljmb/world-candidate.json` ships **5** SIDs (`GOLV2G, PETO2B, PETO5D, VALU1S, VALU4L`). The 4 missing names (`DIML1S, GOLV1S, MURE1S, PETO1S`) **do not exist in the current CIFP source** (`data/cifp/LJMB.dat`) — they're from an older AIRAC cycle. Today's CIFP carries 12 SIDs, of which 7 are blocked by `fixless_leg_unrepresentable_in_waypoint_route_model` (the M1 deferment) and 5 are projectable. Restoring the 9-SID state would require importing a stale CIFP cycle, contradicting `cad/airports/ljmb-authoring.md`'s current authoring sources.

The right answer is **Option (b) — accept the current 5-SID reality**: reshape the helper to a coverage + structural-validity decomposition (per practice-scout best practice for "expected-set" assertions that mirror upstream-data inventories), update the supporting docs to match the 5-SID truth, and archive-flip `D-WORLD.2` per `docs/deferments-CONVENTION.md` §8's three-field locked schema. The on-disk `world-validation-report.json` is auto-regenerated by the test (`outputPath.writeText` at line 152) so it self-heals on first green run.

## Boundaries / non-goals

- **Out: lifting the 7 fixless-leg-blocked SIDs into projectability.** That requires `VI` (heading-to-altitude) leg support in the runtime waypoint route model — `.plan` M1 captures the gap; the SID inventory grows once M1 lands. Out of scope for fn-19.
- **Out: upgrading the CIFP cycle.** Today's `data/cifp/LJMB.dat` is the source of truth; fn-19 conforms to it rather than chasing a newer AIRAC.
- **Out: any change to `WorldCandidateLoader.toWorld()`, `world.validate()`, or the `bin/airport_world_candidate.py` candidate generator.** The candidate is correct; only the test expectation and supporting prose are stale.
- **Out: restructuring the @Test layout.** The existing `@Test fun writesLjmbCurrentCoreValidationReport()` stays as-is; the `assertExpectedLjmbIfrSids` helper it calls is what gets reshaped. No new `@Test` methods unless the existing test layout demands one for clarity (impl-review may push back on overall splitting).

## Decision context

**Option (b) over Option (a)** chosen because:
1. Current CIFP has 12 SIDs total, 5 projectable. The 4 names in the assertion (`*1S` variants) are not in the dataset at all.
2. Restoring them requires a stale CIFP cycle — directly contradicts `cad/airports/ljmb-authoring.md` and the authoring pipeline.
3. The candidate generator (`bin/airport_world_candidate.py:808-857`) is correct: it filters SIDs with `runtimeProjectionBlockers` (`fixless_leg_unrepresentable_in_waypoint_route_model`, the M1 deferment). The 7 blocked SIDs cannot be projected today; that's a runtime-model gap, not a candidate-generation bug.

**Coverage-plus-structural decomposition** (per practice-scout, hardened per plan-review round 1 to resolve the R2/R3 inconsistency the reviewer flagged): the current single-assertion shape treats the test as a snapshot of upstream inventory. The reshape splits the helper's body into **two distinct checks** that produce actionable failure messages:

- **Structural check** (hardened per plan-review round 2 to match R3's actionable two-check shape): loops over each `(key, sid)` entry in `document.world.aerodrome.sids` (a `Map<String, Sid>`) and validates two things: (a) `key == sid.id` — the map key equals the value's id field (data-shape sanity), (b) `"${sid.id}_PATH"` exists in `document.world.geometry.paths` — every SID resolves to a path. **No hard-coded set; no duplicate-key check** (map decode makes duplicate keys unrepresentable); **no "malformed id" check** (concrete definition out of scope — the two checks above are sufficient and actionable). Catches future SIDs that break parsing or path-projection. **Unexpected SIDs are NOT a failure here** — new SIDs appearing structurally are fine (they may be a CIFP cycle upgrade landing more projectable SIDs).
- **Coverage check**: uses an `expectedCovered: Set<String> = setOf("LJMB_SID_GOLV2G_14", "LJMB_SID_PETO2B_14", "LJMB_SID_PETO5D_32", "LJMB_SID_VALU1S_14", "LJMB_SID_VALU4L_32")` and asserts `missing = expectedCovered - actual` is empty. Catches regressions where a SID we promise to keep supporting disappears. **`unexpected = actual - expectedCovered` is NOT asserted empty** — coverage is a subset relation, not an inventory snapshot.

This resolves the R2/R3 inconsistency the reviewer flagged in round 1: the previous wording asserted both directions of the diff, which collapsed coverage back into an inventory snapshot and contradicted the structural test's "new SIDs are fine" framing.

- **R2 (Coverage check, hardened per plan-review round 1):** the coverage check asserts `missing = expectedCovered - actual` is empty (a SID we promised to keep supporting disappeared). It does **NOT** assert `unexpected = actual - expectedCovered` is empty — new SIDs appearing in the candidate (e.g. from a CIFP cycle upgrade) are NOT a coverage failure. The failure message names the missing SIDs and the CIFP cycle id from the source file so the next reconciler knows whether they're on a newer cycle than the test was written against. **Cycle-id extraction rule** (per plan-review round 2 — `data/cifp/LJMB.dat` has no explicit AIRAC cycle marker in the X-Plane CIFP format used here): grep for the literal token `AIRAC`/`CYCLE`/`HDR` in the file header; if no match, **fall back** to the sentinel string `cycle unknown; source data/cifp/LJMB.dat at git-sha <SHA>` where `<SHA>` is the file's blob SHA from `git ls-files -s data/cifp/LJMB.dat | awk '{print $2}'`. Record which path was taken in evidence.
- **R3 (Structural check):** every entry in the `document.world.aerodrome.sids` map validates: (a) the map key matches the `sid.id` field on the value (data-shape sanity), (b) a matching `_PATH` entry exists in `document.world.geometry.paths` for each SID. The structural check runs on `actual` directly — **no hard-coded set, no inventory comparison**. Map-key duplication is not checkable post-decode (kotlinx.serialization decodes into `Map<String, Sid>` which is unrepresentable at duplicate keys); if raw-JSON duplicate-key detection ever becomes a requirement, it lands as a separate parser-level check, not in this helper. Failures name the offending SID id and the specific structural violation. Decomposing the helper into two inner functions (`assertSidsAreStructurallyValid` + `assertSidsCoverPromisedSet`) is the recommended shape; if impl-review feedback prefers the single-helper body, that's acceptable as long as the two semantically distinct failure modes (`missing`, structural) produce separately-named failure messages.
