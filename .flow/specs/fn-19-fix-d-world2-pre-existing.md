# fn-19 — Fix D-WORLD.2 pre-existing :migration:jvmTest failure (LjmbWorldCandidateValidationTest 9-vs-5 SIDs)

## Overview

`migration/src/jvmTest/kotlin/xyz/easiersaid/twr/migration/world/LjmbWorldCandidateValidationTest.assertExpectedLjmbIfrSids` asserts a 9-SID hard-coded expectation (`DIML1S, GOLV1S, GOLV2G, MURE1S, PETO1S, PETO2B, PETO5D, VALU1S, VALU4L`) but the LJMB world-candidate at `cad/airports/rendered/ljmb/world-candidate.json` ships **5** SIDs (`GOLV2G, PETO2B, PETO5D, VALU1S, VALU4L`). The 4 missing names (`DIML1S, GOLV1S, MURE1S, PETO1S`) **do not exist in the current CIFP source** (`data/cifp/LJMB.dat`) — they're from an older AIRAC cycle. Today's CIFP carries 12 SIDs, of which 7 are blocked by `fixless_leg_unrepresentable_in_waypoint_route_model` (the M1 deferment) and 5 are projectable. Restoring the 9-SID state would require importing a stale CIFP cycle, contradicting `cad/airports/ljmb-authoring.md`'s current authoring sources.

The right answer is **Option (b) — accept the current 5-SID reality**: reshape the test to a coverage-policy + structural-validity split (per practice-scout best practice for "expected-set" assertions that mirror upstream-data inventories), update the supporting docs to match the 5-SID truth, and archive-flip `D-WORLD.2` per `docs/deferments-CONVENTION.md` §8's three-field locked schema. The on-disk `world-validation-report.json` is auto-regenerated by the test (`outputPath.writeText` at line 152) so it self-heals on first green run.

## Boundaries / non-goals

- **Out: lifting the 7 fixless-leg-blocked SIDs into projectability.** That requires `VI` (heading-to-altitude) leg support in the runtime waypoint route model — `.plan` M1 captures the gap; the SID inventory grows once M1 lands. Out of scope for fn-19.
- **Out: upgrading the CIFP cycle.** Today's `data/cifp/LJMB.dat` is the source of truth; fn-19 conforms to it rather than chasing a newer AIRAC.
- **Out: any change to `WorldCandidateLoader.toWorld()`, `world.validate()`, or the `bin/airport_world_candidate.py` candidate generator.** The candidate is correct; only the test expectation and supporting prose are stale.

## Decision context

**Option (b) over Option (a)** chosen because:
1. Current CIFP has 12 SIDs total, 5 projectable. The 4 names in the assertion (`*1S` variants) are not in the dataset at all.
2. Restoring them requires a stale CIFP cycle — directly contradicts `cad/airports/ljmb-authoring.md` and the authoring pipeline.
3. The candidate generator (`bin/airport_world_candidate.py:808-857`) is correct: it filters SIDs with `runtimeProjectionBlockers` (`fixless_leg_unrepresentable_in_waypoint_route_model`, the M1 deferment). The 7 blocked SIDs cannot be projected today; that's a runtime-model gap, not a candidate-generation bug.
4. fn-19's bias-toward-(a) hint in the prospect's risk note assumed parity between test and source — repo-scout findings refute that assumption.

**Coverage + structural split** (per practice-scout): the current single-assertion shape (`assertEquals(9, sids.size)` + set membership) treats the test as a snapshot of upstream inventory. Splitting into (a) a **structural test** that loops over `actual` and validates each (catches new SIDs that break parsing — no hard-coded set) and (b) a **coverage test** that loops over an `expectedCovered: Set<String>` and asserts each is present (catches regressions in SIDs we promise to keep supporting) makes future CIFP drift produce actionable diffs ("new SID appeared" vs "promised SID disappeared") rather than cryptic count mismatches.

## Acceptance

- **R1:** `LjmbWorldCandidateValidationTest.assertExpectedLjmbIfrSids` reshaped to accept the 5 currently-projectable LJMB SIDs (`GOLV2G, PETO2B, PETO5D, VALU1S, VALU4L`) as the canonical coverage set. The 4 stale `*1S` variants (`DIML1S, GOLV1S, MURE1S, PETO1S`) removed entirely.
- **R2:** Assertion uses a **set-diff matcher idiom** (compute `missing = expected - actual` and `unexpected = actual - expected`; assert both empty with both names in the failure message). The failure message names the CIFP cycle id from the source file so the next reconciler knows whether they're on a newer cycle than the test was written against.

Both tests live in the same file under distinct `@Test` methods with explicit per-test KDoc explaining the convention.
